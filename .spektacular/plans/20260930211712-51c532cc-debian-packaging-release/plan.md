## Overview

Roost gains its first installable package for Debian and Ubuntu systems plus a repeatable versioned release process. Testers install with the system package manager instead of compiling from source, and every release carries a matching version and notes. This turns today's build-it-yourself session into something shippable.

## Conventions

No always-applied knowledge entries exist for this repo, so these conventions are
drawn from the codebase and CI configuration observed during discovery:

- POSIX shell scripts with `set -eu` and shellcheck gating (CI journey job runs
  shellcheck over `scripts/`): applies to the release script, which must pass the
  same gate.
- Hand-rolled CLI arg parsing in each binary (no CLI framework dependency):
  applies to the `--version` flags, which follow each binary's existing style.
- Green gates before merge: `cargo fmt --all`, `cargo clippy --workspace
  --all-targets -- -D warnings`, `cargo test --workspace`.

## Architecture & Design Decisions

The release is assembled by a POSIX shell script in `scripts/` (same `set -eu` and
shellcheck-gated convention as the existing journey scripts): it builds the four
release binaries from a clean checkout, stages the documented install layout
(binaries side by side plus the login-screen session entry) into a staging tree,
stamps the version everywhere from the git tag, and calls `dpkg-deb` to produce
the artifact. No new build-time tooling is introduced — `dpkg-deb` ships with the
target systems — so the build fetches only declared Cargo dependencies.

Version truth is the git tag (`vX.Y.Z`), injected at compile time through the
environment so every binary's `--version`, the package metadata, and the release
notes agree by construction rather than by manual copying. Each binary gains a
`--version` flag following its existing hand-rolled arg parsing, keeping the
no-new-dependencies posture. A checked-in release checklist plus notes template
makes the cut repeatable, and CI builds the package on every run so packaging
rot is caught immediately.

This beats manifest-driven packaging (rejected: extra fetched tooling) and full
debhelper source packaging (rejected: archive-inclusion overhead for a
non-goal); see `research.md#alternatives-considered-and-rejected`.

## Component Breakdown

- **Release script** (new): builds the four release binaries from a clean checkout,
  stages the install layout, stamps the version from the git tag, and invokes
  `dpkg-deb`. Owns the whole package assembly; fails fast on any step.
- **Version stamp** (changed build behavior): compile-time version injected from the
  environment with tag parsing plus crate-version fallback. Owned by the build, read
  by every binary's `--version` flag and the package metadata generator.
- **`--version` flags** (changed): one per session binary, following each binary's
  existing arg-parsing style. They report the stamped version and exit.
- **Package control metadata** (new, generated): name, version, architecture,
  dependencies on the documented system libraries, and description. Generated by the
  release script from the stamped version so metadata and binaries cannot disagree.
- **Release checklist and notes template** (new docs): the maintainer runbook for
  cutting a release and the per-release notes shape (changes, limitations, supported
  configurations). The checklist drives the release script.
- **CI package job** (changed CI): builds the package artifact on every run so
  packaging rot fails the build. Reuses the existing check-job dependency installs.

## Data Structures & Interfaces

No new persistent data structures. The interfaces this plan introduces or touches:

- **CLI contract**: every session binary accepts `--version` / `-V`, prints the
  stamped version to stdout, and exits successfully without starting the session.
- **Version environment contract**: the build reads `ROOST_VERSION` (a `vX.Y.Z` tag
  or plain `X.Y.Z`); when unset or unparsable, the crate version is used. One
  shared rule, applied identically in all four binaries.
- **Package metadata contract**: the `debian/control`-equivalent fields
  (package name, version, architecture, dependency list, description) are generated
  from the stamped version at package time — never hand-edited per release.
- **Release notes shape**: fixed template sections (changes, known limitations,
  supported configurations) filled in per release.

## Implementation Detail

The plan introduces one new pattern: **build-time version injection without a new
dependency**. A shared compile-time rule (environment variable first, crate
version fallback) gives every binary the same version string; each binary's
`--version` arm is added in its existing arg-parsing style (early match,
print-and-exit), so no CLI framework is pulled in.

The second shape change is **generated, not maintained, package metadata**: the
release script derives the control fields from the stamped version at package
time, so there is no checked-in version number to drift. The staging tree mirrors
the documented install layout exactly (binaries side by side, session entry in
place), making the package a mechanical function of `cargo build --release`
output plus two static inputs (session desktop file, dependency list).

Tests follow the repo's existing shape: unit tests for tag parsing/version
fallback, integration checks that each binary's `--version` output matches the
stamped version, and a script-level test that builds the package and inspects its
contents and metadata (CI runs this on every push).

## Dependencies

- System runtime libraries from docs/install.md (libxkbcommon, EGL/Mesa, GBM,
  glib/GTK for the greeter): become the package's declared dependencies; no changes
  needed to the libraries themselves.
- `dpkg-deb` on the build/packaging machine: used, not changed; ships with all
  target systems.
- Rust toolchain plus the existing Cargo workspace: builds the binaries; no new
  crates or dependencies.
- Spec 20260930211712-51c532cc-debian-packaging-and-release-process: the source
  of truth for scope; already final.
- This spec carries no design references (stated explicitly per discovery).

## Testing Approach

Unit tests cover tag parsing and the version fallback rule (valid tags, missing or
garbage input), since every stamp flows through that one rule. Integration tests
run each built binary with `--version` and assert the output matches the stamped
version, proving the metadata-binaries agreement by construction. A package-level
test builds the artifact and inspects it: control fields present and consistent,
all four binaries plus the session entry in their installed locations,
executable bits set.

These slot into the existing gates: `cargo test --workspace` for the Rust tests,
`shellcheck` for the release script, and a new CI package-build step that fails
the run on packaging rot. Spec success metrics map directly: install-without-
compiler becomes the package-contents test plus a clean-install check; visible
version becomes the `--version` agreement tests; one-pass release becomes the
checklist-driven script itself.

Deliberate gaps: no clean-VM install test in CI (runner scope; documented as a
manual release-checklist step), no upgrade/rollback journey yet (rollback is a
later slice per the spec's non-goals).

## Open Questions

No open questions. Uncertainties resolved during planning: dpkg-deb chosen over
cargo-deb/debhelper (see research.md); version truth is the git tag with crate
fallback; package name `roost`; exact Debian dependency package names verified
at implement time against bookworm/trixie and noble.

## Out of Scope

- Non-Debian formats, hosted apt repo/PPA, rollback/safe-session recovery,
  benchmarks/soak/SBOM, extension distribution (per spec non-goals).
- arm64 packaging: noted as follow-up; first slice targets amd64.
- Clean-VM install test in CI: manual checklist step, not automated.
